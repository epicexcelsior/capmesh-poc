CapMesh Architecture & Technical Brief
A transport-independent capability marketplace protocol enabling autonomous AI agents to discover, evaluate, safely authorize, and verify physical and computational actions on unknown edge hardware.
● Live Hardware Verified (ESP32-C6) ● Transport Independent (BLE + Wi-Fi HTTP) ● Pluggable Settlement (Solana / Channels / Multi-Chain) ● Actuator Oracle Solved (Hardware Pad Readback)
1. The Problem 2. 6-Layer Architecture 3. Physical Delivery Proof 4. Adversarial Threat Matrix 5. Settlement Neutrality 6. 60-Second Demo 7. Repository Map
⚡ 1. The Core Problem: The "Stranger in the Room"
Today, AI agents can easily pay web APIs over HTTP using credit cards or modern protocols like x402 / Stripe MPP. However, when an autonomous agent encounters an arbitrary physical device in real space (a smart lock, micro-charger, optical beacon, relay, or drone), existing systems completely break down.
🚫 Zero Discovery Standard

Matter and Web of Things require heavy pre-commissioning ceremonies, paired accounts, and home hubs. An agent cannot ask an ad-hoc device: "What can you do right now and what does it cost?"

🔒 The Actuator Oracle Hole

A signed receipt saying "yes, the lock opened" only proves the device's software claimed it. Without independent sensor or electrical readback, physical delivery remains unverified.

💸 Micro-Settlement Economics

A physical action may cost $0.001. Paying on-chain L1 gas fees or running heavyweight blockchain RPC on a $4 microcontroller drains memory and makes sub-cent physical transactions uneconomic.

🏗️ 2. The 6-Layer Architecture Model
CapMesh maintains strict decoupling across six distinct functional layers. The physical capability knows nothing about Bluetooth, and the capability protocol knows nothing about the underlying payment blockchain.
Layer 6 • Autonomous Agent & Policy
Agent Policy Engine
Discovers providers, evaluates trust tiers, enforces spending ceilings (€0.1000 limit), discards rogue nodes, selects cheapest verified candidate.
host/capmesh/agent/policy.py
Layer 5 • Capability Protocol (capmesh/0.1)
Standard Capability Protocol
Transport-agnostic JSON schemas for Manifests, Invocation Requests, Execution Receipts, Nonces, and Error structures.
firmware/.../capmesh_dispatcher.c
Layer 4 • Trust & Pluggable Settlement
Payment & Authorization Adapters
Settlement-neutral verifiers (Solana Devnet, Off-chain Payment Channels, Cardano, BSV) + RFC 2104 HMAC-SHA256 authorization tokens.
host/capmesh/payment/verifier.py
Layer 3 • Transport Adapters
Dual Physical Transports (BLE & Wi-Fi HTTP)
NimBLE GATT server (Service 0xCB00) + Embedded SoftAP HTTP server (GET /manifest, POST /invoke, GET /receipt) running concurrently.
ble_transport.c & http_transport.c
Layer 2 • Device Platform Adapter
Device Runtime Bridges
Bridges platform event loops (FreeRTOS tasks on ESP32-C6, Python asyncio on Linux laptop, future Android Seeker) into capability dispatchers.
firmware/esp32/main/main.c
Layer 1 • Physical Actuators & Compute
Capabilities & Hardware Observers
Physical GPIO 8 LED toggle, electrical pad voltage readback, CPU SHA-256 computation, in-memory echo storage. Zero network code.
capabilities/led_capability.c
🔬 3. Solving the Physical Delivery Oracle Problem
When software claims a physical action occurred, how can the buyer verify it? CapMesh incorporates an independent hardware readback observer into the receipt schema.
Hardware Pad Level Verification

On the ESP32-C6, GPIO 8 is configured in GPIO_MODE_INPUT_OUTPUT mode. While the output driver pulses the status LED, the physical input buffer continuously samples the actual voltage on the electrical pad.

🛡️ 4. Adversarial Attack Resilience (Live Tested)
CapMesh defends against physical and protocol-level threats on-chip. All attacks are tested against live hardware during the automated test suite and judging run.
Attack Vector Threat Scenario Defense Mechanism Firmware Result
Replay Attack Eavesdropper intercepts a valid authorization packet over BLE and replays it to activate the actuator again. In-memory circular nonce tracking table with sliding validity window. REPLAY_DETECTED
Expired Authorization Client uses an old authorization token whose expiration epoch has passed. On-chip timestamp verification against local monotonic timer. AUTH_EXPIRED
Parameter Tampering Attacker alters execution arguments (e.g. duration=500s) while reusing the same authorization signature. RFC 2104 HMAC-SHA256 signature verification over canonical canonical message format. UNAUTHORIZED
Rogue / Untrusted Node Malicious Wi-Fi node under-cuts honest prices (0.002 vs 0.004) to lure the agent into executing malicious commands. Agent Policy Engine checks cryptographic trust tier before requesting quotes. POLICY_REJECTED
Runaway Spending Compromised agent logic attempts to execute continuous high-frequency payments. Strict client-side bounded spending ceiling (€0.1000 limit) enforced before signing. CEILING_BLOCKED
💳 5. Settlement Neutrality & Micropayment Channels
To remain completely agile for the TUM Blockchain Hackathon sponsor tracks, CapMesh abstracts payments behind a unified PaymentVerifier interface.
Solana Payment Channels

Escrows a maximum spending ceiling on-chain. The host client issues off-chain signed sequence vouchers for each $0.001 capability invocation, settling on-chain only once.

Solana Devnet L1

Verifies confirmed L1 SPL / SOL transactions via JSON-RPC. Tested with confirmed mainnet/devnet transaction signatures before capability authorization tokens are granted.

Multi-Chain Adapters (TUM)

Pluggable architecture ready to map to announced TUM sponsor tracks (Cardano, BSV, EVM/Base) without touching a single line of embedded firmware or protocol code.

🎬 6. The 60-Second Judging Presentation
The entire live demonstration can be executed with a single command: capmesh demo or ./scripts/run_adversarial_demo.sh.
1
Autonomous Goal & Proximity Discovery

Agent receives goal: "Find a nearby device that can signal me for under €0.01. Use only providers you can verify." Agent discovers two independent devices: ESP32-C6 over BLE (0.004, Verified) and a rogue node over Wi-Fi (0.002, Untrusted).

2
Economic & Security Policy Evaluation

The agent observes that the rogue node is cheaper (0.002 vs 0.004), but inspects its trust tier. The policy engine visibly rejects the cheaper untrusted provider and selects the verified ESP32-C6 under its €0.1000 spending ceiling.

3
Payment Settlement & Bounded Authorization

Agent signs a sub-cent payment channel voucher, computes an RFC 2104 HMAC-SHA256 capability authorization token, and transmits it to the ESP32 over BLE GATT characteristic 0xCB02.

4
Physical Actuation & Hardware Pad Readback

The physical LED blinks on the board. The ESP32's independent hardware pad observer verifies that the voltage on GPIO 8 physically transitioned. The ESP32 signs and returns a verifiable receipt with the delivery proof attached.

5
Adversarial Live-Fire Defense

The agent immediately attempts three attacks against the live board: Replay Attack (blocked on nonce), Expired Authorization (blocked on epoch time), and Tampered Signature (blocked on HMAC). All 3 are rejected on chip.
